## 2. 技术决策与理由

### 2.1 三层分工

```text
Core  负责执行和证明（唯一的业务实现）
CLI   负责稳定调用（argparse，无框架依赖）
Skill 负责指导 Agent（何时调、何时停、什么不能做）
MCP   未来负责跨平台协议适配（只映射，不复制规则）
Plugin未来只负责平台包装（只能调 CLI 或 MCP）
```

理由：数据源、业务指标、宿主平台三者都可能变。把变化点隔离在
「适配器 + 策略 JSON + Skill 文档」三处，Core 与 CLI 就不用重写。

### 2.2 业务规则全部外置到 `config/collection_policy.json`

大小上限、语种配额、题型条数与题量、排除类别、只读白名单、脱敏字段名，
一律写在 JSON 里，代码只做加载与校验。

好处在这次开发里已经体现：`bitable` 导出格式从 csv 改 xlsx，只改了 JSON，
没有动任何一行抽取或采集代码。

`validate_policy()` 会主动检查"业务约束自相矛盾"，例如：

- 题型明细加起来不等于声明的每文档 query 数；
- 某题型题量超出 `[2, 11]`；
- 不同题型题量重复（需求明确要求尽量不重复）；
- `allowed_extensions` 里的格式没配大小上限；
- 某个源没声明 `readonly: true`。

策略错了就退出码 4 并打印全部错误，不允许"带着错误口径往下跑"。

### 2.3 SQLite 是唯一状态源，JSONL/CSV 是导出产物

计划要求可断点续跑。用 JSONL 当状态源会导致"补跑时要重写整个文件"，
用 SQLite 则天然支持按状态查询和 upsert 幂等。

所有报告数字都从 SQLite 现算，不从中间文件读，避免"报告和库对不上"。

### 2.4 内容寻址存储 `artifacts/<sha256[:2]>/<sha256>.<ext>`

同一份内容在两个文件夹里各挂一次时只占一份磁盘，
也为后续正文级去重打了底。落盘走「临时文件 + `os.replace` 原子改名」，
中断不会留下被误当成完整文件的半成品。

### 2.5 语言识别自己实现，不引入 langdetect/fasttext

P0 六语种在字符层面差异极大（拉丁/西里尔/阿拉伯/CJK），脚本判别已经足够稳；
只有拉丁语系内部需要区分，用高频虚词表即可。
两周内不引入需要训练数据或二进制依赖的库，减少 Windows 环境失败面。

不确定时返回 `unknown` + 低置信度，由筛选层转 `needs_review`，
**绝不"猜一个语言然后放行"**。

### 2.6 先确定性，后智能化

文件大小、格式、下载状态、哈希、重复关系由程序判定；
教育属性、学科、可出题性才交给模型。
并且硬性规定：**硬失败不能被模型覆盖**（有专门回归用例）。

### 2.7 不依赖既有 GUI 侧私有函数

`core/doc_processor.py::_llm_call`、`core/smart_crawler.py::_build_full_provider`
都是私有实现，会随 GUI 需求变化。新建 `core/document_collection/llm.py`
独立实现同构逻辑（provider 前缀、extra_body、429/5xx 指数退避），
并把 litellm 作为可选依赖：不可用时显式降级，不伪装成功。

## 3. 缺陷台账

按发现顺序编号。每条都写了**现象 / 根因 / 修复 / 回归用例**，
回归用例是防止同一个坑再踩一次的唯一可靠手段。

### D1　图形主导 PDF 被误判成 needs_review

- 现象：6 页纯图片的 PDF，筛选结果是 `needs_review(language_ambiguous)`，不是淘汰。
- 根因：语言规则排在图形主导之前。正文为空时语言必然是 `unknown`，
  真正的淘汰原因被前一条规则拦截并掩盖。
- 修复：正文为空时先做图形主导判定；`hard_screen` 增加 4b 分支。
- 回归：`test_screening.py::test_graphics_dominance_rules`、
  `test_pipeline_e2e.py::test_screen_hard_rules_reject_out_of_scope_language`。

### D2　采集阶段的硬拒绝在筛选阶段被软化

- 现象：超限文件的本地副本已删除，`artifact.path` 为空，
  筛选阶段判成 `needs_review(artifact_missing)` —— 等于放软了硬门槛。
- 根因：`hard_screen` 只看 artifact 是否存在，不看采集阶段已经下过什么结论。
- 修复：`hard_screen` 接收 `acquire_decision`，硬拒绝原样沿用并标 `hard_failed=True`。
- 回归：`test_screening.py::test_acquire_hard_rejection_is_not_softened`、
  `test_skill_scenarios.py::test_scenario_3_*`、
  `test_pipeline_e2e.py::test_semantic_rejection_cannot_override_hard_failure`。

### D3　report 阶段 JSON 序列化自引用

- 现象：`ValueError: Circular reference detected`。
- 根因：`summary["stage_summaries"] = self.stage_summaries` 塞的是同一个 dict，
  随后 `_result()` 又把 summary 写回 `self.stage_summaries["collection.report"]`，
  形成 `a["collection.report"]["stage_summaries"] is a`。
- 修复：浅拷贝 `{k: dict(v) for k, v in ...}`。
- 回归：`test_pipeline_e2e.py::test_report_and_resume_are_consistent`。

### D4　`RC_EXTRACT_EMPTY` 未导入

- 现象：一跑到空正文分支就 `NameError`。
- 根因：`py_compile` 只查语法不查名字；写代码时以为已经导入。
- 修复：补导入，并把 **ruff（F,E9）纳入固定回归命令**。
  同批清掉 19 处未用导入、1 处未用局部变量、1 处 `_SAFE_ID_RE` 的 `__import__` hack。
- 教训：静态检查必须在第一次运行前就跑，不能等到测试失败才发现。

### D5　lark-cli 的 Windows 垫片吃掉分页 token（最严重）

- 现象：inventory 每个目录只拿到第 1 页（200 条），第 2 页起全部失败：
  ```text
  'v3|wpj...' is not recognized as an internal or external command
  ```
- 根因：npm 在 Windows 生成的是 `lark-cli.CMD`。`CreateProcess` 执行 `.cmd`
  会经 `cmd.exe` 二次解析，而飞书的 `next_page_token` 里含 `|`，被当成管道。
- **为什么危险**：第 1 页正常返回，整体看起来"跑通了"，
  只会体现为总数偏少 —— 属于典型的静默数据缺失。
- 修复：绕过垫片，直接 `node <npm>/node_modules/@larksuite/cli/scripts/run.js`，
  参数由 Python `list2cmdline` 正确引用，不经任何 shell。
  见 `adapters/lark_cli.py::resolve_cli_argv()`。
- 验证：修复后 inventory 得到 4,892 条，与在线计划 1.2 节表格**逐格一致**
  （PDF 2,652/757、DOC-DOCX 456/68、在线 Docx 0/31、PPT-PPTX 0/20、
  XLSX-CSV 38/0、在线 Sheet 8/60、TXT 48/122、MD 601/0、在线 Slides 10/10、
  其他 5/6），这是独立交叉验证。
- 回归：`test_adapters.py::test_page_token_with_pipe_is_passed_as_single_argv_element`、
  `test_resolve_cli_argv_bypasses_cmd_shim_when_possible`。

### D6　本地适配器 item_id 超出 Windows MAX_PATH

- 现象：`extract` 阶段 `FileNotFoundError`，路径长 260+ 字符。
- 根因：`LocalFilesAdapter` 用绝对路径当 `item_token`，
  直接被拿去派生 `extracted/<item_id>.txt`。
- 修复：新增 `contracts.safe_item_id()`。飞书 token（27 位字母数字）保持原样，
  便于人工对照；非安全字符的 token 归一成 `id-<sha256前24位>`。
  派生名上限从 100/80 收到 64，给深工作区留余量。
- 回归：`test_cli.py::test_local_pipeline_end_to_end`（本地端到端全链路）。

### D7　去重代表版本选择让 supplement 源压过 primary 源

- 现象：同一份文件在两个源都出现时，保留的是 `docQA.llm`（supplement）那份。
- 根因：排序键只有「正文长度 → 字节数 → 路径字典序」，
  路径字典序成了实际决定因素，与业务口径无关。
- 修复：按需求第五章口径写成确定性顺序
  **正文更长 → 文件更大 → 有页数定位 → 来源角色 primary 优先 → 路径字典序兜底**，
  并把规则原文写进 `dedup_groups.csv` 的「推荐原因」列（可解释性）。
- 回归：`test_deduplication.py::test_exact_sha_duplicates_keep_one_representative`、
  `test_representative_choice_is_deterministic_and_prefers_richer_text`。

### D8　"文字少"被当成"图形主导"淘汰

- 现象：单页 30 字的封面、文字层损坏的 PDF 被打上 `graphics_dominated` 淘汰。
- 根因：`is_graphics_dominated` 只看字符密度，不看有没有图形证据。
  淘汰理由写错了，业务方无法据此判断该不该救回来。
- 修复：拆成两个判断。`is_graphics_dominated` 必须有图形证据
  （无文字层 / 图片面积占比高且文字稀疏）才判 True；
  新增 `is_text_too_sparse` → `needs_review(text_too_sparse)`。
  同时删掉 screening 里被新分支覆盖的死代码。
- 回归：`test_textstats.py::test_graphics_dominance_needs_image_evidence`、
  `test_screening.py::test_sparse_text_without_image_evidence_goes_to_review`。

### D9　`run_id` 校验放过 `..` / `.`

- 现象：`build_run_config("..")` 不报错。
- 根因：正则 `^[A-Za-z0-9._-]{1,128}$` 允许纯点号，
  而 `run_id` 会直接拼进工作区路径 → 路径逃逸。
- 修复：改为 `^(?!\.+)[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`。
- 回归：`test_config.py::test_run_id_must_be_filesystem_safe`。

### D10　lark-cli 失败时 JSON 在 stderr，错误码全丢

- 现象：所有采集失败都是 `PermanentAdapterError`，`detail.code` 为空。
- 根因：只解析 `result.stdout`。实测 lark-cli 成功时 JSON 走 stdout，
  失败时走 **stderr**（rc=1/2）。
- 修复：`extract_json(stdout) or extract_json(stderr)`；
  `call_log` 记录结构化 `error_code` / `error_message`。
- 回归：`test_regression_real_world.py::test_adapter_parses_error_json_from_stderr`。

### D11　在线文档导出的 code 600 被误判为永久错误

- 现象：80 条样本里 19 条 `pending_export`，错误全是
  `code=600 "hybrid resource expired"`。
- 根因：`classify_error` 的可重试判据里没有这个业务码。
- 实测：同一份 docx 隔几秒重试即成功；但在线 slides 连续重试 3 次仍然 600。
  所以它是**部分可重试**。
- 修复：`_TRANSIENT_API_CODES = {600}` + 关键字 `hybrid resource expired`；
  `1069902 (no permission)`、`131005 (not found)` 仍判永久错误，不浪费重试。
  重试耗尽后如实标 `pending_export`。
- 效果：修复后同样 80 条样本，`pending_export` 从 **19 降到 1**。
- 回归：`test_regression_real_world.py::test_hybrid_resource_expired_is_retryable`、
  `test_no_permission_and_not_found_are_not_retryable`、
  `test_code_600_is_retried_then_can_succeed`、
  `test_persistent_code_600_ends_as_pending_export_not_fake_success`。

### D12　分层抽样一条都没抽到第一个来源

- 现象：`--sample 80` 的 80 条**全部**来自 `docQA.llm`，
  直接违背计划里「知识库_2026 取 30 份、docQA.llm 取 30 份」。
- 根因：按完整层名元组排序后轮转，第一个维度（来源）成了最高位。
  `docQA.llm` 是 ASCII，`知识库_2026` 是中文，前者的所有层都排在前面。
- 修复：重写为**两级策略**
  1. 组间（`source_name`）轮转均分名额，组内不足自动把缺口补给其他组；
  2. 组内（`top_folder` / `extension`）贪心覆盖：优先选"组合新"的条目，
     其次选"维度取值新"的，稀有格式和稀有目录在前几条就会被抽到；
  3. 组间结果**交错合并**，否则 `--sample 80 --limit 10` 又会退化成单来源。
  种子用 sha256 派生（Python 内置 `hash` 每进程随机化，不可复现）。
- 回归：`test_regression_real_world.py::test_sampling_covers_both_sources_even_when_one_has_far_more_strata`、
  `test_sampling_covers_rare_extensions`、`test_sampling_is_reproducible_across_calls`。

### D13　bitable 导出 csv 需要 `--sub-id`

- 现象：`validation` 错误 `--sub-id is required when exporting sheet/bitable as csv`。
- 根因：策略里把 bitable 映射到 csv，但批量场景拿不到子表 id。
- 修复：策略改为 `bitable -> xlsx`，并在 JSON 里记录实测结论。
- 说明：真实清单里没有 bitable（在线资源只有 sheet 68 / docx 31 / slides 20），
  这是提前排掉的坑。

### D14　screen 跑全量把人工复核队列淹了

- 现象：v3 全量筛选 4,892 条，`needs_review` 4,830 条，
  其中 4,812 条是**从未采集过**的条目，`human_review_queue.csv` 完全不可用。
- 根因：`run_screen` 默认取全部条目。没采过的条目没有任何证据可判，
  只能落到 `needs_review(artifact_missing)`。
- 修复：默认只筛"有本地产物或有抽取记录"的条目，其余计入 `skipped_unprocessed`；
  需要全量时显式 `--include-unprocessed`。
  判据用**证据**而不是 status —— 因为 v3 那次全量跑已经把未采集条目的 status
  改写成了 needs_review，用 status 判断会失效。
- 回归：见第 5 节 v4 结果。

### D15　CLI 的 `--semantic` 被策略静默关掉

- 现象：`screen --semantic` 声称强制启用语义复核，实际没有调用模型。
- 根因：`build_llm()` 只看 `policy.llm.enabled`，命令行意图没有穿透。
- 修复：`build_llm(force_enabled=...)`；`query` 增加 `--llm`；`run-all --semantic` 同样穿透。
  模型确实不可用时降级为"仅硬规则"，并把语义项全部转 `needs_review`，不自动放行。

### D16　语种识别误放行（业务风险最高的一条）

- 现象：v4 语义复核后 accepted 5 份，逐份人工核对时发现
  - `Swahili_1.pdf`：128 页**斯瓦希里语**博士论文（坦桑尼亚开放大学），
    被判成 `es`（西班牙语，P0 语种），置信度只有 **0.5442**，
    通过了当时 0.35 的门槛 → 范围外语种被收进最终集，还会占用西班牙语配额；
  - 另有 3 份潜在误放行：两份**乌尔都语**文档被判成 `ar`（阿拉伯语，P0），
    一份**孟加拉语**文档被判成 `en`（英语，P0）。
- 根因两层：
  1. 语种表只覆盖 P0 六语种加少数欧洲语言，而 `docQA.llm` 里真实存在
     swahili / urdu / bengali / tamil / gujarati / marathi / hindi / hausa /

### D19　在线资源导出产物不具备字节级可复现性

- 现象：做完 questions 仍建议 `collection.generate_queries`，编排者照走会空转/重复。
- 修复：`_decide_next` 接收 queries/questions 计数：有 query 无题目 → 推荐
  `generate_questions`；均有 → `report`。

### D25　网关内容审核拒绝与预算耗尽混入一般失败类（2026-09-13，六语种批发现）

- 现象：`Input text data may contain inappropriate content` 的网关拦截被归为"格式无效"
  （`llm_output_invalid`），诱导反复重跑；`finish_reason=length` 的预算耗尽（B1）
  在出题阶段同样难一眼识别。
- 修复：新增 `RC_CONTENT_AUDIT_REJECTED` + `_classify_llm_failure()` 识别 `inappropriate content`
  （改动计划 P2）；出题 JSON 键漂移（法语把 `explanation` 写成 `explication` 等）由
  `llm.normalize_question()` 归一化（P3）。
- 处置口径已写进编排 SKILL.md §6：内容审核**不要重跑**（必复现），预算耗尽**调大 max_tokens**
  （实测 16000→32000 有效）。
- 完整改动清单（P1–P8）见 `docs/结果与验证/改动计划_20260913_P0六语种批.md`。

### 6.4 从 Pilot 得到的可执行结论

1. **抽取链路是可靠的**：70/70 抽取成功，PDF/DOCX/PPTX/XLSX/CSV/TXT/MD 全格式打通，

3. **要达标 P0 配额，抽样必须按语种定向**，不能再做全源均匀抽样。
   建议下一轮直接按目录定向：
   ```powershell

       --source 知识库_2026 --extension pdf --limit 40
   ```

4. **语义复核是主要耗时**：单次分类平均 26 秒，35 份约 15 分钟。

   只对通过硬规则的条目调模型 —— 当前实现已经是这个顺序。
5. **人工抽查不可省**：D16 是自动校验全绿的情况下靠人工发现的。
