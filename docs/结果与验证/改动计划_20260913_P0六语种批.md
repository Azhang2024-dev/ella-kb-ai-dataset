## P1 🟡 放开 query/出题输入窗口到 5 万字符（本轮讨论的核心）

### 现象
- query 生成只把每份文档的**前 16000 字符**（实际是头 50%+中 25%+尾 25% 抽样）喂给模型；
- 与策略自身口径冲突：`query_plan.whole_document_only = true`（query 面向**整篇**文档），但模型看不到整篇；
- 本批 178 份里 **133 份（75%）超过 16k**，`>50k` 有 **62 份（35%）**，英文最严重（29/30 篇论文，中位 77,003 字符，最大 395,433）；
- 截断**静默发生、不报错**，出题质量下限不可见。

### 归因
- 输入侧按**字符数**截断（`truncate_for_prompt`），不是 token 计数，全仓库无 tokenizer；
- `16000` 出现两处且互不知情：`QueryOptions.text_sample_chars`（`query_generation.py:94`）与提示词模板硬编码 `text[:16000]`（`llm.py:365`）——任一处漏改则配置不生效。

### 证据（2026-09-13 实测，真实模型+网关）
对 `alibaba/deepseek-v4-flash-0731` @ `maragate` 打探针（同时预留 `max_tokens=32000`）：

| 输入字符 | 网关 prompt_tokens | 结果 |
|-|-|-|
| 31,500 | 16,193 | OK |
| **50,000** | **25,649** | **OK** |
| 100,000 | 51,204 | OK |
| 200,000 | 102,315 | OK |

结论：① 该网关对中文约 **1.9 字符/token**（比 tiktoken 估的乐观一倍），**5 万字符 ≈ 2.6 万 token**，+3.2 万输出预算 ≈ 5.8 万，远低于窗口上限；② 窗口在 13 万 token 以上，**50k 无风险**；③ 5 万与策略既有 `fast_read_char_window` / `full_text_review_threshold_chars`（均为 50000）口径一致，且与端侧/云侧同为 5 万，评测输入窗口 = 产品入库窗口，对齐正确。

### 计划改动（4 处，须一起改）
| 位置 | 现状 | 改为 |
|-|-|-|
| `config/collection_policy.json` | 无该字段 | `content_rules.prompt_text_chars: 50000`（端侧/云侧同参数的单一来源） |
| `core/document_collection/query_generation.py:94` | `text_sample_chars = 16000` | 默认从 policy 读 `prompt_text_chars` |
| `core/document_collection/llm.py:365` | 硬编码 `text[:16000]` | **删除该处截断**，截断只在 `generate_for_item` 发生一次，消除双截断 |
| `output/_skill_debug/p0-langs-20260913/gen_questions.py` | 硬编码 `text[:16000]` | 同步读 policy（正式化为能力后见 P8） |

### 待确认（动工前需拍板）
1. **截断方式**：保留现有"头 50% + 中 25% + 尾 25%"抽样，还是改为"只留前 5 万"？（建议保留抽样，否则长教材只看前 1/10 会偏）
2. **适用范围**：确认 query 与出题都放到 5 万，`screen` 语义复核维持 12,000 字符（只做分类，不需全文）。
3. **截断留痕**：是否要求把"哪些文档被截、截了多少"写进抽取/生成报告（建议要，否则质量下限不可见）。

### 影响
- 178 份中 62 份（35%）将进入截断口径变化；英语最受影响；
- 输入 token 约 **3 倍**（每份 ~8k → ~2.6 万），178 份 query + 178 份出题，成本按 3 倍输入估。

### 验证方式（动工后）
`validate-config` 退出 0；回归测试（`tests/document_collection/`）全绿；抽 1 份 >5 万字符文档，确认提示词实际长度 ≈5 万且报告记录了截断。

## P2 🟡 内容审核拦截单列分类

- 现象：网关对含敏感内容正文返回 `BadRequestError: Input text data may contain inappropriate content`，当前被归入 `llm_output_invalid`，与非格式问题混淆（本批 2 条）。
- 归因：`query_generation.py` 的错误分支只区分 `LLMUnavailable` / `LLMBudgetExhausted` / 其余→`llm_output_invalid`。
- 计划改动：在 `query_generation.py` 错误分类中，将 `BadRequestError` 且消息含 `inappropriate content` 的失败单列为 **`content_audit_rejected`**，与 `llm_output_invalid`、`llm_budget_exhausted` 并列；报告与状态库单独计数。处置口径：**不重跑**（必复现），换源或如实标注。
- 影响：仅错误分类与报告文案；不改业务结论。

---

## P3 🟡 出题 JSON 键名按语种归一化

- 现象：法语某份文档模型把 `explanation` 写成 `explication`，导致 52 题解析"缺失"（本轮已手工归一化）。
- 归因：出题提示词未声明键名不可翻译；下游按固定键取值。
- 计划改动：出题能力（见 P8）在解析后做**键名归一化**（把 `explication`/`explicación` 等映射回 `explanation`），或在提示词中显式要求键名用英文原样。
- 影响：仅产物字段一致性。

---

## P4 🔴 保证 jsonl 与状态库同写（定向重跑路径）

- 现象：本轮用一次性脚本 `retry_queries.py` 重跑 9 条失败 query，脚本只重写了 jsonl，**漏了 `upsert_query` 落库**，导致状态库（172 份）与 jsonl（178 份）不一致，已手工 reconcile。
- 归因：Core 的 `run_query_generation` 会同时写 jsonl 与库，但"只补失败项"的便捷路径缺失，绕行脚本须自行保证两者一致，易漏。
- 计划改动：① 官方重跑路径明确化（如 `query --status needs_review` 的语义与文档）；② 文档中写明"重跑优先走 CLI，不要自写脚本"；③ 可选：加一个"从 jsonl 重建状态库查询表"的命令，兜住错位（对应上一批 C3）。
- 影响：数据一致性风险，优先级最高。

## P5 🔵 `acquire` 增加语种/目录过滤

- 现象：`acquire` 无 language/文件夹过滤，按语种定向采集只能"先 `inventory --include-subfolder` 收窄、再整批 acquire"两步走。
- 计划改动：给 `acquire` 加 `--top-folder` / `--language` 过滤，或在 inventory 阶段把语种标注写进条目供后续过滤。
- 影响：操作便捷性；不改变结论。

---

## P6 🟡 语种识别阈值按语种区分

- 现象：42 条 `language_ambiguous`（置信度 0.61–0.65 卡在 0.70 门槛下），其中约半数是**正文正常的 zh/fr 学术文档**被误拦。
- 计划改动：① 对非拉丁语种（zh/ru/ar 等）评估单独阈值；② 或改用字符占比类特征替代词频；③ 短期：对复核队列批量放行合格的学术文档。
- 影响：needs_review 队列规模与首轮合格率。

---

## P7 🔵 元数据补全（学科/教育属性）

- 现象：未启用语义复核时 `subject`/`education_level` 全空，入选清单只能用文件名启发式；阿语学科词不在关键词表（ar 仅标出 5/40）。
- 计划改动：① 对清单批次启用 `screen --semantic`；② 关键词表补阿语等学科词；③ 或新增"仅补元数据"的轻量模型能力。
- 影响：清单可信度与按学科配比的可行性。

---

## P8 🟡 把"参考题目生成"提为正式能力

- 现象：Core 无题目生成能力（debug D5），靠 `output/_skill_debug/.../gen_questions.py` 一次性脚本，无参数化、无测试、无产物契约。
- 计划改动：提为正式能力（如 `collection.generate_questions`），复用 litellm 适配器与预算处理，产物契约对齐 `query`；同步落地 P1（5 万窗口）与 P3（键名归一化）。
- 影响：可维护性与可复现性。
