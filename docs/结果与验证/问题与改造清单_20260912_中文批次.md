## A. 环境与基础设施

### A1 🔴 仓库目录被清空（任务开始时发现）
- 现象：scripts/、config/llm_config.json、.venv 全部缺失，目录只剩空 output/ 和一个改名文件夹（内含 603MB 历史 run 证据与一份仓库副本）。
- 归因：会话间隔期间目录被人肉整理；仓库无工作区完整性保护（本地不入库内容无备份），且上一个会话的我曾在未验证移动完成的情况下删除源目录，导致证据永久丢失。
- 已采取：从 internal-gitlab 远端恢复代码；重建 venv；用环境变量重配凭据。
- 改造点：① 仓库加 pre-commit/钩子禁止删除 output/ 下内容；② 关键 run 产物定期归档到网盘；③ 操作纪律：移动目录必须"验证目标完整 → 再删源"。

### A2 🔵 凭据不持久（设计副作用）
- 现象：每次环境事故后 llm_config.json 都要从零配置。
- 归因：凭据按纪律不入库（正确），但没有"无密钥的一键重建"辅助。
- 改造点：提供 scripts/rebuild_llm_config.py（从环境变量读 key，写本地配置），恢复成本从 10 分钟降到 10 秒。

## B. 模型接入

### B1 🔴 reasoning 吞掉 max_tokens 预算（本任务最大技术坑）
- 现象：HTTP 200 但 content 为空；query 生成阶段 5/5 复现 finish_reason=length、reasoning_tokens=6000 打满；题目生成阶段 16k 仍不够（reasoning 打满 16000），32k 才稳定。
- 归因（三层）：① 网关不支持 thinking:disabled（静默忽略不报错）；② 适配器把空 content 归类为 LLMOutputInvalid 可重试错误，但预算不足是确定性失败，重试必然浪费（每次重试 2-5 分钟）；③ finish_reason=length 这个关键信号在 complete() 里被丢弃，排障只能靠裸调复现。
- 已采取：policy llm.max_tokens 3000→16000（query 用）→ 32000（题目用）。
- 改造点：① complete() 捕获 finish_reason=length 时抛 BudgetExhausted 不可重试错误并提示调大预算；② llm.py 按场景区分预算（classify 4k / query_gen 16k / questions 32k）；③ 向网关方提需求：支持关闭思考或返回 reasoning 预告。

### B2 🟡 双层 model 前缀
- 现象："openai/alibaba/deepseek-v4-flash-0731" 这种写法才能跑通。
- 归因：litellm 的 provider 路由前缀与网关的厂商命名空间前缀语义冲突，现在能跑纯靠 OpenAI 兼容网关宽容（把整串当 model 名透传）。
- 改造点：配置模板里写清双层前缀的成因注释；若换严格网关需在 llm.py 做 model 名剥离。

### B3 🔵 litellm 启动拉远程 cost map
- 现象：每次进程启动固定浪费 ~10s（raw.githubusercontent.com 国内超时后才回退本地）。
- 归因：litellm 默认行为，无人关闭。
- 改造点：环境变量 LITELLM_LOCAL_MODEL_COST_MAP=True 写进 run 配置或 README。

## C. 流水线设计

### C1 🔴 生成能力没有条目白名单
- 现象：run_query_generation 只按 status=accepted 取条目，本 run 504 条 accepted（含 444 条假阳性），任务只要 30 份；被迫写驱动脚本绕行，绕行又引发 C2/E1 连锁问题。
- 归因：设计时假设"筛选收敛后 accepted≈目标集合"，没有考虑定向批次场景（硬规则全放行、人工选定子集）。
- 改造点：QueryOptions 加 item_ids 参数（CLI 加 --item-ids/--selection-file），这是本轮最值得做的架构修复。

### C2 🟡 generate_for_item 字段不内聚
- 现象：generated_at/run_id 由标准循环在函数返回后补写；任何绕行者（我）踩 queries.created_at NOT NULL，两次完整重跑。
- 归因：时间戳语义上属于记录本身，却放在调用方；函数契约不完整。
- 改造点：把 run_id/generated_at 移入 generate_for_item 签名（默认参数），或在 docstring 明示调用方义务。

### C3 🔴 jsonl 与状态库可错位，无重建命令
- 现象：后台进程被 kill → query_records.jsonl 停在 21 行；续跑脚本的合并逻辑读旧 jsonl（已不存在）→ 覆盖写成 9 行。状态库 30 份全在，导出视图丢了 21 份。
- 归因：jsonl 逐行 flush、状态库批量 commit，崩溃点不同必然错位；而"状态库是唯一事实源"的原则没有对应的"从事实源重建导出物"的工具。
- 已采取：从状态库重建 jsonl（手写脚本）。
- 改造点：新增只读命令 rebuild-artifacts（从 state.sqlite3 重建全部 jsonl/CSV 报表），任何事故后一条命令恢复。

### C4 🟡 黑名单子串误伤
- 现象：J24 的 query 含"表中"两字被判 query_references_fragment 拒绝（重试换措辞通过）。
- 归因：定位词校验是子串匹配，"表"字命中所有含"表中/表示/外表"的正常中文。
- 改造点：黑名单改分词级/正则边界匹配（如"第X表""见表X"），或允许词白名单。

### C5 🟡 acquire 定向能力弱
- 现象：想采"学术科技类"（J 前缀）只能反复盲跑 --limit（J 类排在 discovered 队列 134-213 位，前后采了 3 轮 60+100+214 才覆盖），期间多采了 400+ 条非目标文件。
- 归因：select_items 只有 extension/source/status 过滤，没有名称模式/类别/关键词过滤；候选顺序是 state rowid（screen 重写 items 后与盘点文件顺序不同，排查时极具迷惑性）。
- 改造点：acquire 加 --name-contains/--name-regex 过滤；日志打印候选队列位置。

### H1 🟡 续跑覆盖校验报告
- 现象：query_validation_report.md 一度只显示 7 份（最后一次续跑只拿自己的 records 写报告）。
- 归因：与 C3 同族——报告从内存记录生成而非状态库。
- 改造点：并入 C3 的 rebuild-artifacts。

### H2 🟡 audit 不支持定向 run
- 现象：13/14 通过，唯一 FAIL 是"两个云盘源都已盘点且用真实名称记录"——本 run 只盘了 DOC-ZH 子目录，属预期。
- 归因：audit 检查点硬编码全源假设，run 的盘点范围没有元数据可查。
- 改造点：run_manifest 记录盘点范围（scope），audit 按 scope 判定该检查点；或提供 --scoped 标记。

## D. 业务口径（需需求方裁定）

### D1 🟡 DOC-ZH 无教材
- 事实：508 条 = 学术论文 80 / 传记 75 / 通俗读物 48 / 新闻 44 / 文宣 30 / 小说 120+；本批 30 份全部是 4-5k 字符的单篇论文。
- 归因：云盘源内容构成与需求"教材/讲义/作业/试卷"形态不匹配；采集计划"宁缺毋滥"原则下只能选论文。
- 待裁定：单篇论文是否满足"大学学习资料"口径；若不满足，中文配额需换源或降低形态要求。

### D2 🟡 语义复核缺位导致假阳性直达 accepted
- 事实：504 条硬规则 accepted 里只有 ~80 条值得出题；本批用"目录类别+人工选定"替代了语义复核。
- 归因：screen --semantic 会对全部 accepted 跑（504 次×26s≈3.6h），成本模型不合理，导致实践中倾向跳过。
- 改造点：语义复核支持与 C1 相同的白名单/抽样参数，让"先粗筛后语义"的成本可控，成为定向批次默认路径。

## F. 题目生成（新增能力）

### F1 🟡 输出字段漂移
- 现象：解答题 7 题的答案写在 reference_answer 而非 answer，初检误报"字段缺失"。
- 归因：prompt 只约束了结构示例，未穷举字段别名；模型对主观题自发使用更语义化的字段名。
- 已采取：归一化 reference_answer→answer。
- 改造点：prompt 明确"answer 字段统一承载答案（主观题为参考答案全文）"；解析侧保留别名归一化作为兜底。

## E. 我的操作失误（自我检讨，不归咎工具）

### E1 🔴 驱动脚本字段漏写
- created_at/generated_at 两处漏写 → NOT NULL 报错 → 两轮完整重跑，浪费 ~40 分钟与模型调用。归因：第一版脚本未对照标准循环逐行核对写库字段，靠报错驱动补齐。

### E2 🔴 截断事故未第一时间发现
- 后台任务被 kill 后 jsonl 已截断，我未检查产物完整性就启动续跑，续跑又覆盖了残缺文件。归因：长任务结束后的第一动作应是"对账状态库 vs 产物"，我没有执行。

### E3 🔴（前一会话）移动后未验证就删源
- 603MB 历史 run 证据不可恢复。归因：违反自己定下的"先验证再删"纪律。已写入长期记忆，并对 output/ 类证据目录的清理增设"必须请示"硬规则。
