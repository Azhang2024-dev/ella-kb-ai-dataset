    fix(document_collection): audit 自身暴露的两个缺陷（D18 阶段摘要被覆盖 / D19 导出产物字节不稳定）
    
    用 audit --compare-with 对比两次真实 Pilot（v4 vs v5）时，检查点 5 报了 3 个 FAIL。
    逐条查证后，2 个是 audit 自身/状态层的真缺陷，1 个是两次运行代码不同导致的预期差异。
    
    D18　stage_state_json 被覆盖，阶段摘要只剩最后一步
    - 现象：v4 的 runs.stage_state_json 只有 {"collection.report": ...}，
      v5 只有 {"collection.audit": ...}，inventory/acquire/extract/dedup/screen 的摘要全丢。
    - 根因：每条 CLI 命令都是独立进程，内存里的 stage_summaries 只有自己这一个阶段；
      StateStore.touch_run() 直接整体覆盖 stage_state_json。
    - 影响面：cost_and_runtime.json 的 stages、resume 的阶段视图、
      audit 判断"是否启用过语义复核"全部失真 —— audit 因此把启用了模型的运行
      当成未启用，错误地强制要求筛选决策逐字一致。
    - 修复：touch_run 改为读出现有 JSON 后合并写入，同阶段再写则更新。
    - 回归：test_touch_run_merges_stage_state_instead_of_overwriting、
      test_audit_after_report_still_sees_the_screen_stage。
    
    D19　在线资源导出产物不具备字节级可复现性
    - 现象：v4 与 v5 的 70 个产物里有 10 个 SHA-256 不同。
    - 查证：按 acquire_mode 分组后，**60 个 download 全部逐字节一致**，
      **10 个 export 全部不同**，且字节数只差几个 byte
      （58435 vs 58471、282343 vs 282327、82106 vs 82105 ...）。
      结论：drive +export 每次由服务端重新渲染，输出不是字节稳定的。
    - 处理：audit 把产物哈希检查拆成两条
      * 「下载类产物的 SHA-256 逐字节一致」-> 硬检查；
      * 「导出类产物字节不稳定属已知事实（仅披露）」-> 列出差异 item_id，不判失败。
      理由：如果把它判失败，检查点 5 会永远红，真正的确定性回归反而被淹没。
      正文级去重用的是规范化文本指纹，不受字节抖动影响。
    - 回归：test_exported_artifacts_are_disclosed_not_failed。
    
    第 3 个 FAIL（条目状态计数 / 筛选决策不一致）是预期差异：
    v4 用的是语种修复前的代码，v5 用的是修复后的代码，
    accepted 从 5 变 6（斯瓦希里语论文被正确拦下，同时若干原本 language_ambiguous
    的条目现在能高置信度正确识别）。确定性阶段（acquire/extract/deduplicate）
    220 条决策逐条一致，盘点计数完全一致 —— 这两项已经通过。
